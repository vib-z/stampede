# Changelog

## Unreleased

- **The cross-client suite.** `tests/test_clients.py` plays one job per client stampede claims (a Herdr chat, Claude, Codex, Cursor, Hermes, Grok Bot, any other bot, a whole remote computer) on the Herdr TUI and on Herdr Core, through the real `stampede` command with that client's environment and process tree, against the fakes, and checks the same outcomes for each: health, start, workers (Cursor refused on Core), a question, a gate (`approve-gate` over SSH only), tell (a Claude agent's inbox; on Core a Codex worker by `hc send --if idle` while idle, at once when done, refused while working), one finish, a reopen that starts nothing, and, for a bot, no polling. A failure reads as `<client>/<backend> <outcome>`. Two gaps for bots are expected failures until fixed: the bot guides' Core start leaves out `HERDR_EVENTS_OWNER`, and a TUI job named by `HERDR_EVENTS_OWNER` does not tag its workspace, so its panes' own alerts miss the bot. [docs/CLIENTS.md](docs/CLIENTS.md) holds the matrix, what differs per client, the live runbook and who does worse; AGENTS.md keeps them current.
- **A whole job on Herdr Core.** `stampede new --core --file <ask.md> [--cwd <repo>]` runs a job on [Herdr Core](https://herdr.dev/core/) (`hc` 0.1.13 or later) in place of the Herdr TUI, which is unchanged: each agent in a Core terminal of its own, with no parent, its brief as its first prompt, and a start outcome from its own status (`STARTED`, `BLOCKED`, `NOT READY` or `FAILED`). When Core loses an answer mid-start, nothing is taken back: `UNKNOWN <agent>`, and `reopen.sh` later adopts or starts it, never a second copy. Whether a launch ran is kept per Claude session (each terminal is labelled with it), so reopen resumes a session that ran (a failed later attempt never undoes that, and Claude's session file is checked before a session counts as never run), starts fresh one that never did, and refuses one it cannot place rather than guess. `start` takes `--cwd` instead of `--pane` (a relative `--brief` is made absolute) and allows one live launch per agent; `tell` prompts Codex with `hc send` by its status, and writes only through `hc send` (`--if idle`; Core refuses a blocked terminal), never a key: text already typed in the prompt (no empty-prompt marker in the last 8 non-empty screen lines), or a slash command such as `/quit`, is refused with the `hc keys` step to do by hand when the worker is idle, so a tell never carries old typed text and never presses a key into a turn or a dialog. A failed `hc` call is one `FAILED <agent> (<reason>)` line or one line on stderr, never a traceback. Cursor stays on the TUI. Install this version before a Core job (`install.sh` or `stampede update`): the lead runs the installed `fleet-job` and the relay hooks run from `~/.local/bin`, so an older copy can end a job without the stamp its follower waits for, and post Core turn ends to the default route. Guide: [README, Herdr Core](README.md#herdr-core); the lead's playbook: [core.md](skills/herdr-fleet/references/core.md); every front-door guide in `remote/` gives the Core choice at its setup, health-check and send steps.
- **One core per job.** `new --core` records the core it ran on (`HC_SESSION`, `HC_SOCKET`) in `<job>/endpoint`; every later `start`, `tell` and reopen works on that core, and a shell set to another core is refused with one line (`HC_SOCKET` at the default socket's own path is the default core).
- **The job's follower, `herdr-event-core`.** It tells the lead when a worker blocks, errors, ends (`GONE`, a hard kill included; an agent's own exit 0 is no `dead` alarm for the bot), vanishes (`LOST`) or a wait terminal ends (`WAITED`), and posts `source` `hc` events to a bot, each with an `event_id`: two episodes on one terminal are two messages, and a permission prompt the agent's own Claude hook also reports is one. It reconnects on its own, only to a core that is up, says `RELAY DOWN` after 10 minutes without one, tells a stall once (`STALE`, and a `stale` event, when a working terminal's screen and status have not changed for `HERDR_EVENTS_STALE_MINUTES`, 30 by default), pushes stalls and ended terminals to the phone when `FLEET_WATCH_NOTIFY=1`, and survives a hung `hc` or relay call; an event the relay did not take is kept and sent again until `herdr-event-post` has queued it (which now records any event for a Core pane, a hook's included, for de-dupe only then, and exits 5 when it cannot queue a follower's), a restart included. `new --core` and reopen check that it is still running 3 s after its start; one that ended is `FAILED`, and `new` takes the job back before any lead.
- **Gates on Core count only the recorded yes.** `approve-gate` also refuses inside a Herdr Core terminal and under a `herdr-core` or `hc` process, so a bot runs it over plain ssh, never `hc exec`. No Core message offers a yes typed into the lead.
- **Reopen and doctor on Core.** `<job>/reopen.sh` checks every folder it may start an agent in first, naming each missing one, then starts only what is not live, reporting each as `start` does (`STARTED`, `BLOCKED`, `NOT READY`, `FAILED`) (`--lead`: the follower and the lead; `--fresh`: new sessions with their briefs, nothing resumed), resumes a Codex worker by the session its own notify recorded after a turn (`codex resume`, with `--no-daemon`), and waits until a restarted lead's own wake hook has delivered both its inbox files; until it has, `<job>/reopen-pending` stays and every later reopen asks again. `herdr-doctor --core` checks `hc`, the selected core, Claude's and Codex's status support; `-h` lists the flag.
- **Owner tags and the roster.** A Core job's owner tag names the core it runs on, and the watchdog asks that core: it expires a finished job's tag a day later with or without the Herdr TUI, and keeps it whenever Core cannot answer; a job folder made again at the same path drops the old tag, and `new --core` refuses that path while an earlier job's terminals still run there. `agents.tsv` is now read, changed and replaced under a lock, so two starts at once never lose a row (on the TUI too, with no change in output).
- **Well-formed ids only.** `herdr-event-post` uses an explicit `workspace` to find an owner tag or job marker only when it is a full Core key (`hc-` and 12 lowercase hex) or holds only letters, digits, `_` and `-`; `--strict` refuses another with exit 6, and an ordinary event drops it.
- **Settings:** `HC`, `HC_SESSION`, `HC_SOCKET`, and `HERDR_EVENTS_DIR`, which moves owner tags, job markers and the default routes folder (default `~/.config/herdr-events`, as before). An empty setting is not passed to a Core terminal. The relay hooks name a stampede Core terminal `hc:<key>/<address>`, so a Codex turn there is no longer dropped. CI also runs a smoke test on a real Herdr Core in a scratch session.

## 0.1.5 (29 Oct 2026)

Plan a job in chat and fork that chat into the lead, a "use stampede" skill that works in any chat, and quieter events while a job is open. One change in behaviour: a bot now gets one done event per job, from `stampede finish`, not one for every turn end. Update with `stampede update` or `herdr plugin update stampede --yes`, which also links the new skill.

- **Quieter events while a job is open.** `stampede new` writes a marker at `~/.config/herdr-events/jobs/<workspace>`. Until `stampede finish <job> "<summary>"` removes it, plain turn ends in that workspace stay on the machine (Herdr done and idle, Claude Stop, idle_prompt, Codex agent-turn-complete). The lead's brief tells it to run finish once when the job is done or stopped for good. That posts one `{source: stampede, state: done, summary}` event through the same relay as a question, then removes the marker. A second finish does not send again. Still sent during the job: blocked, permission prompts, StopFailure, watchdog stale and dead, questions and gates. Blocked and permission prompts for one pane are one message for 120 seconds, whichever source arrives first. A Codex turn with no Herdr pane is not sent. A workspace with no marker behaves as before. Tested with the relay sample payloads and fake Herdr.
- **"Use stampede" works in any chat.** The front door is now its own skill, `skills/stampede`, which `install.sh` links into `~/.claude/skills/` and `~/.codex/skills/` beside the other three, and `herdr-doctor` checks. In any project chat (the Claude desktop app or a Herdr pane), "use stampede: ..." sizes the job, writes the ask, runs `herdr-trust` on the project, opens a Herdr workspace for it and starts the lead with `stampede new`, forked from the chat when the plan was worked out there. Before this, only the three playbook skills were installed, so a fresh chat had nothing that answered to "stampede". The root SKILL.md now points to it. Run `stampede update` (or `herdr plugin update stampede --yes`) to get the new link; a `stampede` skill of your own is left as is.
- **Fork the planning chat into the lead.** `stampede new --fork <session id>` starts the lead as a fork of that Claude chat (`claude --resume <id> --fork-session`, with the lead's hooks), so a job you planned with Claude in the desktop app or a Herdr pane keeps the whole conversation; the lead writes the agreed plan into `plan.md` instead of planning again. A front-door chat passes `--fork "$CLAUDE_CODE_SESSION_ID"`. A value that is not a UUID exits 2 before anything is made, and the reopen record leaves the fork out. Guide: [remote/claude-code.md](remote/claude-code.md#plan-here-then-fork-the-lead).

## 0.1.2 (23 Oct 2026)

- **Small jobs stay in Herdr:** a small job still needs no stampede job, but it runs as one agent session in a single Herdr pane of its own, tagged with `herdr-events-owner` and prompted with `herdr-send`, never as a bare agent CLI call over SSH or nohup outside Herdr. Updated in herdr-fleet, grokbot-herdr, SKILL.md and the README.
- **Gate questions go back to whoever started the job.** `stampede new` records the starting bot (`HERDR_EVENTS_OWNER`, else the workspace's owner tag) in `<job>/owner`. In a bot-started job, `stampede ask` sends a `question` event to that bot instead of a phone card, and both go through `herdr-event-post --strict`: only that bot's own route with a URL, never the default route, and a refusal unless the event is queued. A queued question or gate waits out a route with no URL instead of being dropped, and its lead gets an `UNDELIVERED` line in `inbox.log` when it is held and if it expires after 24 h; events carry `lead_pane`, not `pane`, so the flusher never drops one for a later turn end, and each answer names its question. `stampede ask --gate --sha <commit> [--pr <n>] "<action>"` sends a `gate` event to that bot, which asks you in chat and records your yes with `stampede approve-gate`; a job started locally asks on your phone through `FLEET_ASK_CMD`, as before. A yes typed in the lead's pane always works. The lead acts on a recorded yes only after `stampede gate-ok` matches it to the gate and the commit; a push after it withdraws it, and `approve-gate` refuses inside Herdr, for a local job and for another commit. The relay sends every gate as its own event.
- **The README flowchart is a live mermaid block again**, left to right, showing the gate question going back to Grok Bot, Moshi only for a job you started locally, and a yes typed in Herdr. "Only when they pay" is now "only when it's worth it". The README opens with the story, before anything else: the Grok Bot is the inlet that spins up local agents over Tailscale, then the chain from you to Grok to your stampede bot to the lead to its agents and back. Then the Grok Bot flow: it starts and ends with the bot, each bot owns its own Herdr workspace, the lead is the valve that passes each worker only the context it needs, recommended for everyone and not required. The Herdr plugin description leads with the same sentence.
- **Plugin updates keep stampede working:** run from a Herdr-managed checkout (`<plugins>/github-installations/stampede-<id>/<N>-<M>/checkout`), `install.sh` moves a link that points at the same file in another `<N>-<M>/checkout` of that same install to the new one (`relinked`), so a `herdr plugin update` or reinstall no longer leaves it to dangle once Herdr deletes the old checkout. Paths are compared as plain text; another plugin's link, a backup's, a different file's or one of yours is still left as is, and a clone relinks nothing.
- **herdr-doctor:** for a GitHub-managed plugin, a `PROBLEM` when `stampede` or a skill link resolves outside the checkout `herdr plugin list --json` reports; a `warn` when the `FLEET_TRUST_ROOT` folder (default `~/code`) is missing, in place of an `ok`.
- **stampede update in a plugin install:** Herdr's managed checkout keeps `.git`, so a checkout whose path ends in `plugins/github-installations/stampede-<id>/<N>-<M>/checkout` counts as a plugin install too (an ordinary clone under a folder of that name does not). `stampede update` changes nothing there, and it and the daily check name `herdr plugin update stampede --yes`, not `git switch main`.
- **Docs:** the README Install shows the plugin route with the PATH line and `herdr-trust`; Updating has `--yes` and a one-time path from 0.1.0; SETUP.md has the uninstall commands for a managed install (link targets compared as plain text, never a `find -lname` pattern) and the `~/.cache/stampede` note, and no longer calls the plugin "needed only for the event relay".

## 0.1.1 (23 Oct 2026)

- **Updating:** `stampede update` fast-forwards a clean checkout on `main` and reruns `install.sh`; it refuses local changes, untracked files, another branch, or an ignored file the update would overwrite, and outside a git checkout names `herdr plugin update`. Once a day, `stampede --version` (on stderr), `stampede update --check` and `herdr-doctor` (a `warn`) say when a newer GitHub release is out; silent offline or on any failure, off with `STAMPEDE_NO_UPDATE_CHECK=1`. The README has an [Updating](README.md#updating) section.
- **One version:** `herdr-plugin.toml` matches VERSION, and a test keeps them equal. [RELEASING.md](RELEASING.md) says how to cut a release.
- **One version, wider:** the version test also checks the README badge, the README's `stampede --version` line and the site's install prompt against VERSION.
- **A clean core install:** `herdr-doctor` runs the core checks only and exits 0 on a clean install with Herdr running. The event relay checks run when the relay is installed, or with `herdr-doctor --relay`. Exit 0 ok, 1 a `PROBLEM`, 2 usage.
- **A short README top and macOS CI:** the README opens with what stampede is, a 3-command install, a first ask, a flow diagram and its limits. CI (`.github/workflows/ci.yml`) runs the tests, the install and `herdr-doctor` against a real Herdr on macOS, on every push and pull request.
- **Size the job first:** before any workspace, the lead or front door sizes the job on length, agents, risk and durability. A small job needs no stampede (one Claude session with built-in subagents); a big one runs as a stampede job. The rule is in [herdr-fleet](skills/herdr-fleet/SKILL.md#size-the-job-first-small-or-big), linked from SKILL.md, grokbot-herdr and the README FAQ.
- **Site:** the landing page is rebuilt around the film: a frosted header with a theme toggle, the Open gate mark's full run with a red beat and no outlines, one gold Get started that copies the install prompt and says to paste it into your agent, and a short footer. Live at https://vib-z.github.io/stampede/ and https://stampede-xi.vercel.app/.

## 0.1.0 (22 Oct 2026)

The first public version: one ask, one lead, and only the panes that pay.

- **The job:** `stampede new` makes a job folder and starts a Claude lead with its hooks; the lead plans in `plan.md` and starts work at once.
- **Workers:** `stampede start` starts Claude, Codex or Cursor in a Herdr pane, in auto mode, with hooks that report back; no polling.
- **Questions and gates:** `stampede ask` puts a question on your phone through Moshi while the lead keeps working; every merge, push to a shared branch, deploy, send, spend and close waits for your own tap.
- **Share the plan first**, on request: `--review` and `stampede approve`, locked to the plan's fingerprint.
- **Front doors:** a Herdr chat, Claude or Codex desktop, Cursor, Grok Bot and other bots, or a whole remote computer.
- **Reopen:** `reopen.sh` brings a closed job back.
- **Install:** `install.sh` links three skills and the commands; `stampede --version` prints the version.
