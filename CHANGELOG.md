# Changelog

## Unreleased

A job on Herdr Core now runs the way Core itself works. The lead is a root terminal, every helper is its real Core child, and everything goes through Core. The shape every client reads: [docs/CORE-NATIVE.md](docs/CORE-NATIVE.md).

- **`stampede new --core` starts a Core-native job.** The lead is a root Core terminal; the space is its name label (`--space`). Each helper started with `stampede start` is a Core child of the terminal that started it, at any depth, and ends with its parent unless `--outlive-parent`. A helper is Claude, Codex or any program (`stampede start <job> <name> -- <program>`). Messages go only through Core: `hc send`, Core's notes about each child, `hc wait --children`, and results in files with the path sent. There is no follower terminal, no inbox files and no hooks.
- **A cap and a queue.** At most 12 helpers work at once in one lead's tree (`--max-helpers`, `<job>/max-helpers`, `STAMPEDE_MAX_HELPERS`). A start over the cap prints `QUEUED`; `stampede next` starts queued helpers when there is room.
- **Layout labels.** The lead is the first terminal of tab `main`; helpers fill `main`, `main-2` and so on, 4 to a tab (`STAMPEDE_TAB_PANES`), or a workstream tab with `--tab`. Labels only: Core's tree never depends on them.
- **New commands for a Core job:** `stampede next`, `tree`, `snapshot`, `reopen` and `close`. `tree.json` is the reopen record, and `REOPEN.md` and `reopen.sh` are rendered from it. `reopen` rebuilds the tree parents first, a resumed Claude agent labelled `stampede.resumed=1`. `close` ends a subtree leaves first; a whole-job close leaves `<job>/closed`, which keeps the watchdog quiet until `reopen` removes it.
- **The lead is watched for the owner.** A blocked, failed, dead or stalled lead reaches the owner from the machine's watchdog sweep (`herdr-event-core --sweep`), once per episode. Questions, gates, posts and finish work as before.
- **The earlier Core path is `stampede new --core --relay`,** kept for one release. It is still the one way to hand Cursor, Hermes or Kimi to a Herdr TUI pane. Its reference is now [core-relay.md](skills/herdr-fleet/references/core-relay.md).

## 0.1.10 (13 Nov 2026)

A Codex lead on Codex 0.167.1 gets its workers' reports and your messages again, a bot that started a job now hears every post from its lead, and the fleet skill's default shape is now thinker and doer: the lead plans once at high effort, and workers follow its spec at medium effort. One change in behaviour, for bots: in a job a bot started, `stampede post` now also sends that bot a `post` event, and exits 2 when the relay refuses it. Update with `stampede update` or `herdr plugin update stampede --yes`.

- **A Codex lead on Codex 0.167.1 gets its lines again (Herdr TUI).** Codex 0.167.1 draws its empty-prompt footer as `← for agents · ? for shortcuts`. stampede looked for a footer row that starts with `? for shortcuts`, so it took every empty prompt for a draft and never typed `stampede tell` text or inbox lines (`TURN`, `REPORT` and the rest) into a Codex lead's pane; its deliverer gave up after 4 hours. Codex's last row, below the last prompt line, now only has to contain `? for shortcuts`. One above the prompt still does not count, and a draft, which hides that row, still holds every line, even one that quotes the phrase. `herdr-send` (which types a lead's brief pointer) and the Herdr Core check already looked for `for shortcuts` anywhere on the last lines, so they are unchanged; tests now pin the new footer for all three. Checked live on Linux in a Herdr 0.9.5 pane with Codex 0.167.1: its empty prompt reads as idle and a typed draft as busy. No hook settings changed. Finding F16 in [docs/CLIENTS.md](docs/CLIENTS.md).
- **A bot hears every post.** In a job a bot started (and no front door), `stampede post` used to write only `<job>/outbox/`, which only a front door's `wait` reads, so the bot never heard the lead's plan, files or report. Now it also sends that bot one `post` event (`source` stampede, `text`, `outbox`, `item`, `files`, no `pane`) on the same strict route as a question, and prints `POSTED NNN to <bot>`. When the relay refuses, the outbox item stays, nothing says `POSTED`, and the command exits 2 with one line naming the item and the fix (`herdr-doctor --relay`, then post again). Front-door and local jobs are unchanged. The lead's brief in a bot's job now says how to reach the owner with `post`, and the bot's guides say what to do with a `post` event: show the owner the text and files; there is nothing to answer.
- **A post waits out a route with no URL, as a question does.** When the bot's route loses its URL after a post was queued, `herdr-event-flush` holds the post instead of dropping it, and tells the lead once in `inbox.log`: `UNDELIVERED post outbox NNN for <bot> held: ...`, saying not to post it again, since it goes out by itself once the route has a URL. After 24 h it moves to `dead/`, and a second `UNDELIVERED` line says the bot never heard it and to post again.
- **Thinker and doer is the default fleet shape.** The herdr-fleet skill now has the lead plan once, at high effort (Claude `xhigh`, Codex `ultra`), and write a tight spec for each task: what to build, which files, what done looks like and which tests to run. It plans again mid-build only when a worker is blocked. Workers build at medium effort by default and follow the spec without redesigning it; the lead raises one to high or xhigh only for a task it flags as hard. A cheap test named in the brief runs after each worker step, and the lead runs the full checks once after it integrates the work. Review is one pass at the end, Codex by default and always on another model than the builder, looped again only for a real bug (broken behaviour, a failing test or a regression); style and wording notes go in the report. A plan review is now optional: only when the owner asks or the plan is high risk. The owner can change any of this for a job. This changes the skill's guidance only, not a command.

## 0.1.9 (11 Nov 2026)

stampede now keeps up with Herdr Core 0.1.20: a message waits while you are typing in an agent's terminal, a Codex lead can run a Herdr Core job, a Core job can show in the Herdr app if you ask for it, and `herdr-doctor` checks whichever of the Herdr TUI and Herdr Core you have installed. The evals that came with the Linux work are part of this release, with every failure they found fixed. Two changes in behaviour: a standing `FLEET_LEAD_KIND=codex` now gives a Herdr Core job a Codex lead too (it used to stay on Claude), and plain `herdr-doctor` now also checks Herdr Core when `hc` is installed. For bots: `approve-gate` requires `--digest`, which the gate event's `approve` line already carries. Update with `stampede update` or `herdr plugin update stampede --yes`. Herdr Core 0.1.13 is still the minimum; 0.1.20 is the one to run, and `herdr-doctor` warns below it.

- **A message waits while you type (Herdr Core 0.1.20).** Core now holds a message while a person has an unsent draft in the terminal, for up to `draft_wait` seconds since their last key (60 by default). `stampede tell` waits with it and prints `SUBMITTED` once the message went in alone. When Core's hold runs out it types the message after the draft, so stampede stops its send 10 seconds before that could happen (after 50 seconds by default): a draft you began and then left is never submitted with a tell. A send that Core cancelled is one `FAILED` line saying nothing was typed; every `hc` call now has a time limit, so a hung or stopped one is a `FAILED` line too, with the terminal to read before you send again. `SUBMITTED` adds a note when Core saw no turn start. stampede keeps its own check for text already in the prompt. Measured on a real core and repeated as live eval C13.
- **A Codex lead on Herdr Core: `stampede new --core --lead codex`.** The lead runs in a Core terminal of its own, without its daemon, with its brief as its first prompt. It has no file hook, so each new line for it is typed into its terminal with `hc send`, only while it is idle or done, marked `[fleet-job inbox for <lead>, not typed by the owner]`; the job's follower starts that for its own lines. Each line is typed at most once: after a send with no answer, nothing more is typed into that terminal until it has taken a turn, then the lead is told where to read the lines itself, and a reopen's line is not taken as acknowledged. Because that typing is unattended, a Codex lead on Core needs a running Herdr Core of 0.1.20 or later with `draft_wait` at 30 seconds or more, resolved as the running core resolves it (its own config as TOML, else its environment's fallback), and is refused otherwise; the same value limits every send. Its first turn end records its Codex session, and `reopen.sh` resumes it. `FLEET_LEAD_KIND=codex` now applies to Core jobs; `--fork` still takes a Claude lead. A lead restarted on the other CLI gets its brief rewritten for it on Core as well. Run live with a stand-in for Codex (eval C14), not yet with a signed-in Codex.
- **See a Core job in the Herdr app, if you ask: `--app-space`.** Off by default. `stampede new --core --app-space` (or `STAMPEDE_APP_SPACE=1`) labels the lead and workers `herdr.space=stampede-<key>` and `herdr.tab=<agent>`, the app's own labels, so the job shows as one space with a tab per agent; the follower and wait terminals stay out. It is an opt-in because the app turns keep on for a terminal it shows, and closing a pane there ends that agent. Checked on a real core by its labels (eval C16); how the app draws it was not looked at.
- **A kept terminal that loses its agent is told once, as gone.** With keep on, Core replaces a lost program (a signal, a reboot, a crash) with a shell at the same address, name and labels. The follower now handles Core's `lost` and `restarted` events: one `GONE <agent> <reason> exit - (a shell is in its place at <address> ...)` line for the lead, one `dead` event for the bot when it was working, and never an idle or turn event for the shell. `tell` refuses the shell by name, `start` and `reopen.sh` no longer take it for the agent (with keep still on or turned off since), and `reopen.sh` starts the agent again in a new terminal under a free name. Every launch now carries a label of its own (`stampede.launch`), so a start whose answer was lost finds its own terminal and never an older one. Run live with `hc keep` and `kill -9` (eval C15).
- **The follower decides on every event type Core sends.** `lost`, `restarted`, `keep` and `labels` are handled; `title`, `size`, `doc` and `foreground` are named as no news; a test fails when Core's schema lists a type with no decision. A stream that has sent Core's heartbeat (every 15 s) and then says nothing for 60 s is reopened, so a hung stream no longer waits for the 10 minute `RELAY DOWN`.
- **Herdr Core's API is pinned and checked.** `hc schema` for 0.1.20 is committed (`tests/fixtures/hc-schema-0.1.20.json`). `tests/test_hc_contract.py` holds every `hc` command the product runs, the fake `hc` the tests use and the follower's event decisions to it, and live eval V03 compares it with `hc schema` on the machine. The fake learned the draft hold, `keep`, `label` and `cancelled`.
- **`herdr-doctor` checks each backend that is installed.** The Herdr TUI when `herdr` is on PATH, Herdr Core when `hc` is. With both, one usable backend is enough: the other's gaps are a `warn` (the Herdr TUI's event plugin among them), and `ok backend tui,core` (or one of them) says where a job can run. `--tui` or `--core` checks one, with each gap a `PROBLEM`. So a machine with Herdr Core and no Herdr TUI server passes. New warns on Core: `hc` older than 0.1.20; on macOS, terminals opened before the core's current bundle was installed; a core started from inside an agent or a pane, with `hc server restart --fresh` as the fix for you to run. A missing `claude` is a warn when `codex` is there. It never starts, stops or restarts a core.
- **`new` names `--core` when the Herdr TUI cannot take the job.** With no Herdr server (or no `herdr`, or no workspace outside Herdr) and a Herdr Core answering on its socket, the one error line adds how to run the job on Core. The Herdr TUI stays the default backend, and nothing changes when it is running.
- **Kimi reports its status on Herdr Core, and still runs handed.** Kimi 2.5.3 showed OSC 7501 status on Herdr Core 0.1.20 (at its trust dialog, in a scratch home). It has no turn hook and its empty prompt is unknown, so stampede still hands it to a Herdr TUI pane, and the refusal says why. Cursor and Hermes stopped at their sign-in screens in that probe and were not taken further.
- **Live evals on a Mac for both backends.** `tests/evals/live/tui_scratch.sh` runs the TUI cases in a scratch home with a Herdr server of its own, checked by its socket path before anything starts or stops; the TUI runner's outside-Herdr commands run with pid 1 as parent, so they hold from inside a Herdr pane. New cases: D10 and D11 (fixture), C13 to C16 and V03 (live Core). Results before and after: [tests/evals/README.md](tests/evals/README.md).
- **Versions.** Checked against Herdr Core 0.1.18 (on macOS the core is its own app, Herdr Core, with its own local network and microphone prompts; `hc` and `herdr-core` in `~/.local/bin` are links into it), 0.1.19 and 0.1.20, and the Herdr app 0.1.13 to 0.1.15 by its notes. The Herdr TUI had no release in that week: 0.9.5 is still current. CI and the Linux eval container pin Herdr Core 0.1.20 by checksum. Jobs on another machine (`hc run --on`) are not supported yet: a job is local to one machine.

Also in this release, from the evals and the live Linux work of 8 and 9 Nov: every failure the new evals and the live Linux and Core runs found is fixed; one documented ceiling stays (an agent that detaches to pid 1 as the same user can still run `approve-gate`). A yes now covers exactly the gate you were asked. One change for bots: `approve-gate` requires `--digest`, which the gate event's `approve` line already carries, so a bot that runs that line as given needs no change. A yes recorded by 0.1.8 or older for a gate still open is refused, so the lead asks that gate again.

- **Evals.** `tests/evals/` holds the dataset (`cases.json`: the owner's yes, side effects, lifecycle, portability, dependencies, versions, a Linux install, live Herdr TUI and live Herdr Core cases), the fixture runner (`run.py`: 58 cases through the real `stampede` command against the fakes), the live runners and the recorder (`record.py`: one scrubbed run with its environment, digests and tool versions). The runs before these fixes and after are in `tests/evals/runs/`, one harness for all: on main's code 16 of the 58 fixture cases failed on macOS and on Ubuntu, and C08 on a live Herdr Core; on this branch none. CI runs the fixture cases on macOS and on Linux.
- **A yes covers the gate as asked.** The approval record holds a digest of the gate (action, PR, commit, route); `gate-ok` refuses a gate changed after the yes, and the `approve` command a bot or front door is handed carries the digest (`approve-gate --digest`, required), so a gate edited between the question and the yes takes none. A malformed gate or approval record is refused in one line.
- **No process table, no approval.** `approve-gate` refuses when `ps` cannot run, fails, or does not show the command and every ancestor up to pid 1, instead of taking a partial table for "not inside Herdr". On a Linux host whose `/proc` hides other users' processes (`hidepid`), a bot's `approve-gate` over SSH is therefore refused.
- **`finish` cancels the job's questions still waiting on the phone.** Their waiters run in a session of their own, which outlives the lead's pane, and since Herdr Core 0.1.19 a Core terminal too. `cancel` signals only the process that still runs that very question (its argv names the job and the question's id; a pid file can outlive its waiter), and one bad record never stops the rest.
- **Herdr's own errors are one line.** A command that Herdr refuses, or a program that cannot run, prints `fleet-job <command>: <error>` and exits 1, as Herdr Core's already did (finding F4 in docs/CLIENTS.md, fixed).
- **`herdr-doctor` checks Herdr's version:** 0.9.4 or later, and no readable version is a `PROBLEM`; an `hc` that prints no version is told apart from no `hc`.
- **The relay says when its lock was not taken** (`lock-not-taken` in its log), still sends the event, and leaves the de-dupe file alone, so an unlocked writer can repeat an event but never loses another writer's record.
- **The scripts find tools where Linux keeps them:** the relay, the plugin hook, `herdr-doctor` and `reopen.sh` add `/usr/local/bin` and Homebrew's Linux prefix to the bare PATH of a timer or a Herdr plugin.
- **`reopen.sh` uses the installed helpers, else this checkout's,** and exits 5 when it cannot tag the new workspace for its bot, instead of carrying on silently.
- **`reopen.sh` moves an open job's marker to the workspace it reopens in** (with `<job>/workspace`), so Herdr's plain turn ends there stay on the machine and `finish` clears the right marker; found live on Linux. `--into` takes only a workspace id that is open and holds no other open job, and checks all that before it changes anything. After a Herdr server restart, when the job's workspace is back with plain shells, it says so and what to do instead of refusing without a reason.
- **Linux, live.** On Ubuntu 24.04 arm64 with the real Herdr 0.9.5, Herdr Core 0.1.19 and moshi-hook 0.4.50 (stand-in agents, nothing signed in): the install, `herdr-doctor`, the Herdr plugin, a whole TUI job and a whole Core job. [docs/LINUX.md](docs/LINUX.md) holds the matrix, what was real and the gaps (systemd user timers, x86_64 live, signed-in agents, Moshi paired, a bot over SSH).
- **Versions, as of 8 Nov.** Checked against Herdr 0.9.5 (it stopped installing Codex turn hooks; stampede's own Codex notify hook and Herdr's screen detection still give the lead its turns), Herdr Core 0.1.19 (detached programs outlive their terminal, hence `finish` above; `hc server restart` keeps the core's environment and the job's terminals) and moshi-hook 0.4.50 (`ask`, `notify`, `job` unchanged). The minimums stay Herdr 0.9.4 and Herdr Core 0.1.13.
- **CI** adds Herdr 0.9.5, Herdr Core, `herdr-doctor` and the Core smoke run on Linux, with Herdr Core pinned by checksum on both systems.

## 0.1.8 (4 Nov 2026)

You can now choose the lead for each job, Claude or Codex, and the event relay runs on Linux as well as macOS. On Herdr Core, a yes typed into a job terminal now gets a short reply that says where to answer instead. A job started without `--lead` runs exactly as before, with a Claude lead. Update with `stampede update` or `herdr plugin update stampede --yes`. Linux has passed the unit suite, the relay samples and the install in CI and in a container, but no live job has run on a real Linux machine yet.

- **Linux, beside macOS.** The event relay, `herdr-doctor`, `install.sh` and `fleet-watch.sh` run on Linux. File size, age and mode use one helper (`herdr-platform`), so GNU `stat` and BSD `stat` both describe the file. The relay log is `~/Library/Logs/herdr-events.log` on macOS and `${XDG_STATE_HOME:-~/.local/state}/herdr-events.log` on Linux. On Linux `install.sh` enables systemd user timers (`herdr-event-watchdog.timer` every 5 minutes, `herdr-events-flush.timer` every 2 minutes) when `systemctl --user` answers, and otherwise starts one flock-guarded `herdr-event-supervise` loop. `--no-supervise` skips that. `herdr-doctor --relay` checks launchd, those systemd timers, or the loop, whichever this machine uses. The de-dupe lock is exclusive on both, `lockf` on macOS and `flock` on Linux, and is let go before the flush. The loop counts as running only when its pid file names a live `herdr-event-supervise`, so a stale pid file is never trusted or signalled. The Herdr plugin lists `linux` as well as `macos`. CI runs the unit suite, the relay samples and the install on Linux too. On Linux, systemd user timers need `loginctl enable-linger` on a machine nobody logs in to, and the flock loop needs `install.sh` again after a reboot. Not run live on Linux yet.
- **Pick the lead: `stampede new --lead claude|codex`.** Claude stays the default, and a job started without the flag runs exactly as before. `--lead codex` starts the lead on Codex (GPT-6 Astra, `ultra`) with its notify hook and `--approve-for-me`, network access in its sandbox (Herdr's socket, `git push`, `gh`) and write access to the repo's `.git` and `<jobs root>/worktrees`. `FLEET_LEAD_KIND` makes either one your standing choice. Its brief pointer is typed into its pane at once (`BLOCKED`, exit 1, when it does not go in). It works with `--pane`, `--workspace`, `--front-door` and `--review`; `--fork` (a fork is always a Claude chat) and `--core` (a Core lead is Claude) refuse it with exit 2 before anything is made. Another value exits 2. A lead restarted with `stampede start <job> <lead> --kind claude|codex` keeps its CLI's lead model and gets its generated brief rewritten for that CLI.
- **A Codex lead is woken without a file hook.** Every line for it still lands in `inbox.log` or `inbox/<lead>.md`; a short-lived deliverer (`fleet-job _deliver`, started by the workers' hooks, `tell`, answers, gate approvals, its own turn ends and `herdr-event-flush`'s `UNDELIVERED` line) types the unread lines into its pane as one prompt marked `[fleet-job inbox for <lead>, not typed by the owner]`, only while it is idle or done, unfocused and with nothing typed in its prompt (Codex shows its `? for shortcuts` footer only while its prompt is empty, so any other screen counts as a draft). Read offsets move only after `SUBMITTED`; one deliverer runs at a time; every Herdr look and `herdr-send` it runs has a time limit, so a stalled one never holds the lock; it gives up after 4 hours (`<job>/hooks/deliver.log`). The lead's own turn ends go to the relay (`herdr-event-codex-notify`), never to `inbox.log`.
- **A Codex lead acts on a gate only after `gate-ok` prints `APPROVED`,** as on Herdr Core: text is typed into its pane, so a yes there proves nothing. Its brief, `ask --gate`, `approve-gate`, `gate-ok` and the relay's messages no longer point it to a yes typed in its pane.
- **`FLEET_LEAD_MODEL` and `FLEET_LEAD_EFFORT` apply as a pair to the CLI the model belongs to:** a `gpt-...` model sets a Codex lead, any other model (or none) a Claude lead, as before. A Codex lead started from a config with Claude settings keeps GPT-6 Astra at `ultra`.
- **On Herdr Core, a typed yes gets an answer.** Typing a gate approval into a Core job terminal used to get no reply. The lead now answers with one line: "A typed yes does not count on Core; answer in the chat or on the phone that started this job." Gates still open only on a recorded yes, and the Herdr TUI is unchanged. Tests check the lead's brief and that `yes`, `approve` and `go ahead` leave Core gates closed for every client. Not yet checked with a live agent.

## 0.1.7 (31 Oct 2026)

A chat outside Herdr can now run a job and pass on everything the lead has for you, job folders move out of your repos, a new test suite plays a job from every client stampede supports on both backends, and a Herdr Core job can hand Cursor, Hermes and Kimi workers to Herdr TUI panes. One change in behaviour: a new job folder goes to `~/code/herdr-jobs/jobs/` (`FLEET_JOBS_ROOT` moves it), not into the repo; old in-repo jobs keep working. Update with `stampede update` or `herdr plugin update stampede --yes`. A Core job with handed workers needs this version installed, because the lead and the relay run the installed copies.

- **A front door outside Herdr relays for you.** From a real job: you talked only to the Claude desktop chat, but the lead showed its plan, cards and files in a pane nobody watched, an "ok" to the chat's summary was passed on as plan approval, and answers sat unread behind a card. `stampede new --front-door` now marks such a job. The lead posts what is for you with `stampede post <job> "<text>" --file <path>` into `<job>/outbox/`, and a hook turns its own AskUserQuestion and SendUserFile into posts. The front door waits with `stampede wait <job>` in the background (no foreground sleep), sends you each item and relays your answer. Questions and gates go to the outbox; the front door records your yes to a gate with `approve-gate`, quoting your words, and an explicit order you already gave in its chat for that exact action counts. In a front-door job `approve` refuses a plan the lead did not post exactly as it stands, and one the front door has not yet received through `stampede wait`, so a yes given before the chat even had the plan can never approve it. The lead's rules: [front-door.md](skills/herdr-fleet/references/front-door.md); the front door's loop: [skills/stampede](skills/stampede/SKILL.md).
- **A front-door job always reaches its end.** The lead's `finish` posts a `done` item to the outbox, `stampede wait` returns `LEAD_GONE` when Herdr no longer has the lead, `approve` refuses to run from inside Herdr (the lead could approve its own plan) and checks `fleet-plan.md` as well as `plan.md`, `new --front-door` is refused in a bot-owned workspace, and the lead's brief names the exact `fleet-job` that started the job, so an older one on PATH cannot lack `post`.
- **`stampede tell` no longer says DELIVERED to an agent held at a question card.** It queues the message, prints `BLOCKED_ON_CARD <agent>` and exits 3; `stampede wait` reports the same.
- **Job folders leave the repo.** Every job folder is now `~/code/herdr-jobs/jobs/<date>-<bot or local>-<slug>/` (`FLEET_JOBS_ROOT` moves the root), with the repo in `<job>/workdir`; every agent gets `--add-dir <job>` to write there. The same name twice in a day gets `-2`. Nothing goes into `.git/info/exclude` any more. Old in-repo `.herdr-*` jobs keep working.
- **The cross-client suite.** `tests/test_clients.py` plays one job per client stampede claims (a Herdr chat, Claude, Codex, Cursor, Hermes, Grok Bot, any other bot, a whole remote computer) on the Herdr TUI and on Herdr Core, through the real `stampede` command with that client's environment and process tree, against the fakes, and checks each outcome's command contract for each (the agents' own work is for the live runs): health, start, workers (Cursor refused on Core), a question, a gate (`approve-gate` over SSH only), tell (a Claude agent's inbox; on Core a Codex worker by `hc send --if idle` while idle, at once when done, refused while working), one finish, a reopen that starts nothing, and, for a bot, no polling. A failure reads as `<client>/<backend> <outcome>`. Eight gaps are expected failures until fixed, each named after its finding. Two are for bots: the bot guides' Core start leaves out `HERDR_EVENTS_OWNER`, and a TUI job named by `HERDR_EVENTS_OWNER` does not tag its workspace, so its panes' own alerts miss the bot. Six were found by the live runs: a Herdr refusal at start ends in a traceback, a TUI lead does not get the front door's `FLEET_ASK_CMD`, a phone card does not name its job, `start` checks the brief before the kind, a bot's answer command holds its placeholder shell-quoted, and the finishing turn wakes the bot after its done. [docs/CLIENTS.md](docs/CLIENTS.md) holds the matrix, what differs per client, the live runbook and who does worse; AGENTS.md keeps them current.
- **Mixed jobs: Cursor, Hermes and Kimi in a Herdr Core job.** Core runs only agents that report OSC 7501 status, so `stampede start <job> <agent> --kind cursor|hermes|kimi --pane <pane id> --brief <file>` hands one to a Herdr TUI pane at its shell prompt, under the same launch lock and one-live-launch rule as a Core start (across both: a pane or a Core terminal running that name, or Herdr unable to say, refuses it). The pane is claimed first, atomically: a pane another launch holds, of any job, still starting or with its agent there, refuses the start before anything changes. Its `core.json` entry (`backend` `tui`, the pane, a new `launch` id, the exact start) and the pane's mark in `$HERDR_EVENTS_DIR/handed/` are written before Herdr starts it; it is `STARTED` only once Herdr shows its name in the pane and took its brief pointer (`briefed`); the pointer passes `tell`'s checks, so a draft, an unknown empty prompt (Kimi's, today) or a busy agent leaves it `NOT BRIEFED`, with the `tell` to send by hand. A start that fails gives back a stale mark it took over. A lost answer is adopted when a whole agent list shows it in the pane, else `FAILED` (saying the CLI may still run there undetected, and how to end it), or `UNKNOWN` with both kept for reopen.
